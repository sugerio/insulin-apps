# Fixture-only KMS + TSA evidence protocol

**Experimental synthetic-data test only; not production sealing or independently security reviewed.** The separate Node command seals one checked-in, hash-pinned synthetic fixture; it never accepts an existing envelope, PDF, digest, database or endpoint. The Worker and its mock completion are unchanged. Revocation and DigiCert licensing have not been checked. This document describes the implemented test and its limits, not permission to use real data, shared resources or deploy.

## Isolation and frozen D3

The fixture was generated by `synthetic-seal-fixture.ts` using the actual Worker signing, evidence-checking and delivery code in a new in-process Miniflare D1/R2 environment. It contains fictional Ana and Marcus, synthetic timestamps and D0–D3; the local mock signing chain and artifact hashes were checked before export. The checked-in complete fixture bundle is SHA-256 pinned in `synthetic-seal-fixed.ts`. The sealer validates that exact bundle and recreates its output files in a fresh private temporary workspace. On resume it checks existing files against the pinned fixture before sending any new signing or timestamp request. D3 is the exact frozen delivery PDF produced by the fixture; it is not regenerated after hashing. The D3 local-only disclaimer remains unchanged.

The existing envelope schema has no reliable synthetic-content provenance. A test-domain address, local mode or caller-supplied marker does not prove that PDF content is synthetic. Consequently there is no command to seal an existing envelope or arbitrary bytes. `start` makes a new workspace; `resume` only accepts a correctly named private workspace in the process temporary directory and validates the pinned fixture. The fixture pin and code are part of the trusted program, not protection against a local user who changes the program or has equivalent operating-system privileges. Keep code and temporary workspace away from untrusted local users. No existing Worker data, mock evidence or COMPLETED status is changed.

## Bytes, cryptography and verification

The versioned schema and field order define the canonical UTF-8 JSON manifest M (`json-stringify-schema-v1`). It binds D0–D3 SHA-256 hashes and lengths; ordered signature records, artifact links, previous/event hashes, OTP and consent timestamps; synthetic designation; public-key fingerprint; and algorithm identifiers. Schema, canonical bytes, event links and all four artifacts are independently checked. It does not assert identity, reading, intent or legal facts.

Let H = SHA-256(M). KMS Sign receives H as `DIGEST` with `ECDSA_SHA_256`; S is its DER signature. P-256 key metadata, KMS response key identity and S over M are checked. The saved SPKI is bound by its SHA-256 fingerprint; the separate verifier must be given that fingerprint independently (for this test, obtain it separately from the authorized KMS alias). A saved public key alone does not establish AWS origin.

The RFC3161 request asks for certificates and uses imprint SHA-256(S). Its 16-byte nonce is the first 16 bytes of SHA-256 over the domain string `esign-synthetic-tsa-nonce-v1\n` followed by S. This ties the nonce to the authenticated, nondeterministic KMS ECDSA signature, makes it unpredictable before that signature, and prevents a resumed workspace from injecting caller-chosen bytes into the public TSA request; retries of the same signature reuse the exact nonce. It is not independently generated randomness, and its unpredictability depends on KMS signature randomness. Its derivation is named in M. M excludes S, its own hash, the request and the response, and D3 excludes its own hash and the later seal: no self-reference is used.

The independent offline verifier takes the expected SPKI fingerprint and a trust bundle separately from the evidence. It rechecks exact fixture bytes, canonical manifest and chain, public-key type/fingerprint, KMS signature, nonce derivation and the reconstructed request. OpenSSL `ts -verify -queryfile` checks response status, imprint, nonce, token signature, timestamping certificate purpose and certificate chain. Tests used a local test CA and OpenSSL 3.6.4, including wrong imprint, nonce, status, malformed or altered response, wrong roots and a poisoned `SSL_CERT_FILE`. The verifier prints verification time, OpenSSL version, expected key fingerprint and trust-bundle SHA-256; it does not trust a saved success flag. Other OpenSSL versions and trust stores have not been independently validated. Revocation is **not checked**, and commercial eligibility/licensing is **not verified**. An HTTP TSA request carries only the synthetic signature imprint and derived nonce but is not confidential.

## Persistence, recovery and limits

D0–D3, M, SPKI, S, nonce, exact request and verified response are separate files in the new private temporary workspace. Publication writes and fsyncs a private temporary file, hard-links it into place without replacement, then fsyncs the directory. A losing concurrent writer verifies and reuses the winner; ECDSA signatures and TSA tokens need not match. After the directory fsync and successful re-read and validation of that winner, the publication is committed even if unlinking the private temporary candidate fails. The process attempts to warn without printing its private path and preserves the leftover (a failed logger may not display the warning); it may be a hard link to the winner or a different valid losing candidate. It can contain sensitive test data and consume disk space. It must not be modified, removed or treated as WORM. If publication or winner validation has not succeeded, cleanup failure does not turn the error into success or hide the primary error. Existing conflicting or corrupted files fail closed; do not overwrite or delete them. Resumption checks prior steps and reuses verified signature and response bytes. A failed remote response or process crash before publication can result in another KMS signature or TSA issuance; there is no exactly-once remote issuance. Filesystem behavior has only been tested locally and is not WORM; a privileged local user can mutate evidence.

Tests cover concurrent publication, concurrent fixture orchestration with fake adapters, a real subprocess SIGKILL after timestamp request persistence and recovery, and a subprocess SIGKILL after hard-link publication before directory fsync. They do not exercise every crash boundary, power loss, filesystem or platform. A crash can leave temporary files; preserve and investigate them. No automatic deletion or repair of retained crash leftovers is attempted. No claims are made about production recovery or immutable retention.

See README for the explicit opt-in command, independent verification procedure and live-test results. The local test is restricted to the authorized profile (`ESIGN_AWS_PROFILE`), region `us-west-2`, key alias `esign-local-test-signing`, and public DigiCert endpoint. No cloud resource creation, deployment, real documents or real users are authorized.

## Interactive generated envelopes

The fixture-only description above continues to apply to the separate fixed-fixture CLI. The opt-in interactive path described in README uses a distinct, isolated persistent Worker/D1/R2 instance. Its server generates the source PDF and fixed fictional recipients and exposes no upload or recipient-edit routes to the browser. After the actual two signing views and mock finalization, it checks the local chain, freezes D3, and binds that envelope's D0–D3 and ordered events using the same canonical manifest and KMS/TSA algorithms. A private, conditional instance-to-evidence-workspace link selects one winner before external calls; all retries compare the current checked evidence with that workspace before reuse. Incomplete or conflicting evidence is rejected. The offline dynamic verifier checks cryptographic consistency against an independently supplied key fingerprint and roots; it does not by itself prove the source was synthetic. The trusted local service, code, private instance and operating-system file permissions provide that provenance. The loopback HTTP service does not authenticate local operating-system users; a local process can forge browser headers. Use only on a trusted, single-user machine. A local process or privileged attacker is outside this experiment's protection. Local persistence and hard links are not WORM, and crash/power-loss guarantees are limited to the tested filesystem and boundaries.
