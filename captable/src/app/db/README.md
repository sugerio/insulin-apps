# Database

The app has one SQLite database: Cloudflare D1 when published, a local file in the preview.

- `schema.ts`: the tables, in Drizzle's SQLite dialect.
- `client.ts`: `getDatabase()`, a Drizzle handle on the database.
- `migrations/`: `0000_init.sql`, additive generated migrations, and the `meta/` journal, generated by Drizzle Kit from
  `schema.ts`; and `0001_ledger_triggers.sql`, a custom migration holding what Drizzle can't express: the
  `transaction_types` seed and the triggers that protect the ledger and the records (append-only rows, `version`
  checks, state transitions, the ledger head).

Documents are capped at 10 MiB and uploaded in 256 KiB chunks. Measure near-cap uploads and streamed downloads on a
real Cloudflare D1 database before raising that cap; the local SQLite adapter cannot reproduce D1's BLOB transport or
Worker memory costs. Failed uploads can leave rows in `document_upload_chunks`, which are invisible without document
metadata. Each due-processing pass deletes at most 100 staging rows older than a day. The AppBuilder data panel shows
the `document_blobs` rows directly, including their BLOB values; keep the 256 KiB chunk size so each row and a page of
rows remain modest.

## Change tables with triggers only by adding

SQLite can't alter a constraint in place, so for such a change Drizzle Kit rebuilds the table: it creates
`__new_<table>`, copies the rows, drops the table and renames the copy. Dropping a table drops its triggers, so the
rebuilt table loses its protections. If another table's trigger refers to the rebuilt table, the rename fails, and by
then the old table is already gone. For `audit_events` and `document_links` the generated rebuild fails anyway,
because drizzle-kit 0.31 re-creates their expression indexes with the expressions quoted as column names.

Many core tables have triggers; inspect `0001_ledger_triggers.sql` before changing one. On a table with triggers:

- **Do:** add a table; add a nullable column, or a column with a default (a single-column `.references()` is fine);
  add an index or a unique index.
- **Don't:** add or change a `check()`, a default, `.notNull()`, a column type, a primary key or a multi-column
  `foreignKey()`; drop or rename a column or the table. Enforce a rule for a new column in the server, or with a trigger
  in a custom migration.

The platform asks this of every table anyway. While a new version publishes, the version already serving shares the
database, so every change must stay backward compatible and additive while older code can still be serving.

## The build checks it

`npm run build` runs `node scripts/check-ledger-triggers.mjs` first, and publishing runs `npm run build`. The check
replays the migrations in journal order on an empty in-memory database, one statement per `--> statement-breakpoint`
chunk. It stops the build when:

- a statement fails;
- a chunk is empty or holds more than one statement (the preview runs only the first);
- a trigger that a migration created is missing at the end, unless a later migration removed it with `DROP TRIGGER`.

It reads everything from the migration files, so there is no list of triggers to maintain. `test/db` checks the rest:
schema, trigger behaviour and retry safety.

AppBuilder agents can't write, edit or delete migration files. If the check fails after `npm run db:generate`, revert
the change in `schema.ts` and tell the user that the generated migration must be removed before the app is published.

## Custom migrations (developers)

```sh
npx drizzle-kit generate --custom --name <what_it_does>
```

This writes an empty `migrations/<NNNN>_<what_it_does>.sql` and its journal entry. In that file:

- Put one SQL statement in each chunk, and separate chunks with a line `--> statement-breakpoint`.
- Make every statement safe to run again: `CREATE TRIGGER IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`,
  `INSERT OR IGNORE`, `DROP TRIGGER IF EXISTS`. The next section explains why.
- To restore triggers after an intended rebuild, copy their `CREATE TRIGGER` statements from the migration that
  created them, in the same order. SQLite fires the newest trigger first, and that order decides which error a write
  sees when several triggers reject it.

Never edit a generated migration or the journal. To remove a migration that has not been published, run
`npx drizzle-kit drop`. Run `npm run build` and `npm test` before committing.

## When a publish fails while migrating

Publishing applies pending migrations with `drizzle-kit migrate` over D1's HTTP API, which sends one request per
statement. A migration is recorded in `__drizzle_migrations` only after all of its statements have run. A failure
midway, such as a timeout or a dropped connection, leaves the earlier statements applied and the migration unrecorded,
so the next publish runs it again from its first statement.

- **A custom migration** here can run again safely, so just publish again.
- **The first publish** runs `0000_init.sql` on a new, empty database. If it fails midway, the retry stops at the first
  `CREATE TABLE` with "already exists". The database holds no data yet, because the app's code is uploaded only after
  its migrations succeed. Start it over: have the platform operator delete the app's D1 database (it carries the app's
  Worker name), then publish again, and the publish creates an empty database and applies every migration. Never do
  this for an app that has served traffic, because its database holds the company's records.
- **A later generated migration** that fails midway must be repaired before the next publish: undo the statements that
  ran (in the D1 console) so that it can run from the start. Keep generated migrations small, because a one-statement
  migration can't fail halfway.
