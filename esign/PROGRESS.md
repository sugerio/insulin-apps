# Local E-sign progress

## Implemented local slice

The existing untracked experiment has been preserved. The Worker exposes tenant API-key management, single-PDF template upload and immutable-by-conditional-create source storage, single-template envelopes, explicit D0 preparation, and **explicitly local-test-gated** recipient page APIs. The React recipient page exchanges a short-lived one-use code bound to the allowed host origin, requests a synthetic test-mail OTP, verifies it before fetching the PDF, and requires individual consent. The key stays on the management side. Test-mail delivery stores plaintext OTPs only in a separate local R2 bucket and accepts only `example.com` or `.test` addresses; no real mail adapter exists. Each message has a unique ID exposed to the local page, so simultaneous envelopes for one email do not overwrite each other.

The OTP challenge has a per-task persistent 15-minute budget, five verification attempts, a send cooldown and a three-send window. Resend or a new session does not reset that budget. An expired verified session can obtain a fresh view and reverify within those limits. OTP currently binds to the task/session rather than an independent recipient reusable across multiple documents. A successful OTP can be retried with the same code and still-authorized session if its response is lost; document loading has a separate retry. Names the local Helvetica renderer cannot encode or fit on its fixed-size signature page are rejected for every recipient at envelope creation. Width validation sums individual glyph advances without kerning, matching the renderer’s PDF `Tj` output. Before each signature, all names are checked again and the database batch asserts they did not change. Previously recorded pending jobs also fail safely if their name cannot render; already generated PDFs are not retroactively corrected. Older envelopes or jobs can therefore be blocked and need manual handling; there is no termination endpoint.

Signing atomically checks trusted session, persisted OTP, consent and current input artifact/hash and writes a signature fact, hash-linked signature event and pending job. The caller explicitly processes each job: input bytes are hash-checked, a signature is appended to a shared signature page (adding a continuation when full), and the output is conditionally created and persisted before the next task activates. Sign, process and local finalization support tested retry paths. Local finalization checks artifact hashes and the signing-event chain, writes an immutable-by-conditional-create test manifest and fake HMAC-based KMS/TSA tags, and marks the local envelope COMPLETED. The synthetic timestamp is derived from the last recorded signing time and is not an independent timestamp. Test adapters, software keys and local COMPLETED are **not production evidence or a production-ready state**.

There is **no automatic queue scanner or unattended recovery**. The caller must request preparation, processing after each signature and finalization, and poll for progress/reminders. Retrying handles the tested R2-write/D1-failure case; orphan objects can still exist and require manual investigation. Local R2 conditional creation is not WORM and privileged mutation is possible. No signing endpoint is available without explicitly configured local-test bindings and keys.

## Preview race and resource limits

Each preview now renders in its own detached container and only the latest completed load can commit; replacing or leaving a preview aborts the PDF.js loading task and active page render. Older concurrent fetch responses are ignored. Pixel budgets enforce 16,777,216 pixels per page, 50,331,648 total, and an 8,192-pixel dimension limit before canvas allocation; failure clears partial canvases and blocks signing. These budgets are not a limit on all PDF parsing, decoded-image, or input-buffer memory; an ongoing Blob read cannot be cancelled. Interleaved retry and stale-fetch regressions were observed failing before the fix. Tests also cover per-page/total limits, active-render and loading cancellation, pre-aborted work, and the UI refusal to sign on rendering failure. A separate headless Chrome 156 sandbox harness again rendered two synthetic pages and rejected malformed input; it does not exercise the full signing flow.

## PDF.js damaged-content handling

A synthetic inline image missing bits-per-component reproduced the review finding: real PDF.js 5.4.624 rendered successfully with default error handling while omitting the image. A Chrome 156 test also showed that `stopAtErrors: true` alone still let the render resolve: PDF.js can mark an operator list complete after a stream error. The preview now enables that option and requires a genuine final operator-list chunk, failing closed if the pinned version's internal hook is unavailable. Real PDF.js tests cover the damaged PDF, a valid inline image, and the recipient UI refusing signing on the failure; a local headless Chrome sandbox harness confirmed valid rendering and damaged-image rejection. This hook relies on a private PDF.js method and must be revalidated before upgrading the pinned dependency. It and `stopAtErrors` do not detect every damaged or incomplete PDF and do not make PDF parsing reliable or production-ready.

## Remaining limitations and blockers

Not a complete production system. No independent recipient model / same-recipient multi-task OTP reuse, multi-template envelopes, URL import, template editor, Nitro, Drizzle schema, complete audit event coverage or independently trusted evidence exists. The local React page has simulated interaction tests and a targeted Chrome rendering harness, but not a full automated real-browser signing flow. PDF handling and the standard-font restriction need further work. Object reconciliation is manual and some ambiguous failure paths need additional independent review. Fake HMAC test sealing is neither KMS nor TSA; no genuine secure email, managed KMS, external TSA or verified WORM is present. ## Shared signature pages

New jobs persist their page count and occupied slot with the corresponding output in the same database batch. The first signer adds a page after the original pages; later signers use the verified predecessor output and its trusted server-side layout, with eight fixed non-overlapping slots per page. Each output remains distinct. Signing against older outputs without layout records is now rejected atomically before recording a signature, event or job. All previously recorded non-first pending jobs without the new signing-time layout snapshot fail processing and require manual handling, without fabricated layout records; pending first jobs with incompatible old orphan objects also fail closed. Local integrity checks do not protect against privileged mutation. D3 remains a separate delivery artifact and the local evidence seal is not production proof.

## Signing-time input validation

Before committing a signature, input bytes are hash-checked and parsed, and a predecessor layout must match the actual page count. The D1 signing batch compares the input key and layout with the values read and stores a snapshot atomically with the signature, event and job. Processing uses the captured snapshot, so later changes to the predecessor layout do not redirect it. This is not protection against privileged database mutation or R2 mutation after the read: a changed object can still make an already-recorded signature fail processing. No normal path was found that deletes the predecessor layout.

## Pre-snapshot migration blocker

A real pre-0012 pending non-first signature remains safely blocked after migration, even if the predecessor output, current layout, input hash and page count match. The older signing event did not bind the mutable layout, so those checks cannot prove the historical slot and backfilling would invent a signing-time fact. The process endpoint now returns `signature_input_layout_missing` (409); README gives a read-only query and evidence-preservation steps. This may also indicate a lost snapshot, not necessarily a legacy job. No signing facts or statuses are changed, no recovery or termination is claimed, and the upgrade incompatibility remains a blocker for recovery and production. No normal path deleting a layout was identified.

## Conservative upload completion recovery

New upload instances use a durable versioned protocol marker and a one-shot attempt marker before finalization or remote calls. Failures, interruptions, partial workspaces and older instances without this marker require investigation; no automatic retry or unlock is offered. Only a fully unsigned stage with both source hashes, expected tasks and no extra envelope objects is reported NOT_READY. Full signing uses the existing complete evidence verification. The page retains a local uncertainty guard across refresh; it is not a security boundary against other browsers or local actors. Synthetic tests cover corruption, failure, restart, concurrent status and ambiguous responses; this is not WORM or production evidence.


Upload review fixes: completion explicitly returns the envelope ID; a test applies the real first HTTP response to the upload page. Per-instance in-process request coordination prevents status checks and mutations racing completion. Completion/investigation blocks recipient session, OTP, signature and processing mutations and the UI closes the signing frame. Coordination does not protect against multiple host processes sharing one instance; that remains prohibited.


Preflight crash follow-up: each local upload preflight and state/evidence inspection durably publishes a unique start marker before validation. Only a successfully validated unsigned preflight or successful inspection publishes its matching safe marker; unmatched markers fail closed across restart even if a separate investigation marker cannot be written. Completed signing moves to the existing durable attempt marker before finalization. Control markers are append-only and accumulate; coordination is in-process only, and sharing an instance across hosts remains unsupported. Tests exercise real host SIGKILL at preflight, failed investigation marker publication and restart, and repeated safe unsigned preflights.


Publication cleanup follow-up: after a directory-synced winner is independently re-read and validated, failure to unlink its private candidate triggers a best-effort warning but does not turn the durable commit into an apparent failure. The leftover is preserved, may be a winner hard link or a different losing candidate, and consumes space. Earlier publication/validation errors still fail and remain the primary error if cleanup also fails. Tests reproduce concurrent cleanup failure and the safe-marker plus investigation-marker double fault across restart.


Safe-marker publication review follow-up: a safe marker may be visible after a hard link even though directory sync or winner verification fails; simultaneous failure to write the investigation marker cannot be reliably recorded on the same failing filesystem. Safe markers therefore describe checks, not durable authorization to continue. Only an instance created in the current host can be modified. Every resumed upload is read-only INVESTIGATE, including untouched and successfully sealed instances; existing final PDF/certificate reads and separate offline verification remain available. Tests inject both failures and use a new host subprocess to verify the restart restriction without altering the marker evidence. This intentionally disables recovery rather than asserting persistence the filesystem cannot guarantee.

### Editor asynchronous preview race fix

A review found that an aborted PDF render could finish asynchronous cleanup against the shared visible container after a newer render had already appended its first page, leaving an incorrectly numbered, saveable preview. Each editor render now owns a detached container; only a non-aborted, fully completed render is committed to the visible host, and cleanup removes and releases only that render's own canvases.
