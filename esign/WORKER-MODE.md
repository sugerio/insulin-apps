# Worker mode: configuration and deployment

E-sign is one Worker, `src/worker.ts`; [README.md](README.md) describes what it does. This page
covers how it is configured, run and deployed. Do not deploy, change cloud resources or send real
mail without authorization for that account, and use synthetic data only.

| Where | How | Configuration |
|---|---|---|
| Tests | `app.fetch(request, env)` with Miniflare bindings | the `env` object passed in |
| Locally on workerd | `npm run dev` (`wrangler dev --local`) | `wrangler.jsonc` and `.dev.vars` |
| Cloudflare, `esign-dev` | `node scripts/deploy.ts --target dev` (CI, see Deploy) | generated from the environment, plus Worker secrets |
| Cloudflare, `esign-prod` | `node scripts/deploy.ts --target prod` (CI, by hand from `main`) | the same |

## dev and prod: one switch

`ESIGN_ENV` (`src/environment.ts`) is the one switch: `dev` locally (`wrangler.jsonc`) and on
`esign-dev`, `prod` on `esign-prod`. `scripts/deploy.ts` sets it from the target (`--target prod`
is prod, any other target is dev); unset means dev. Everything else is a value for the environment
(addresses, origins, keys), never a second switch.

| | dev | prod |
|---|---|---|
| One-time codes and signed copies | with a sink (`MAIL_SINK`), to that mailbox, naming the intended recipient; without one, to their recipients (marked as dev); without mail configured, codes only for `example.com` / `*.test` addresses and nothing is emailed. Every code is also kept in the test mailbox | to their recipients |
| Test mailbox (`TEST_MAIL` bucket, `GET /v1/test-mail/:id`) | every code is kept there, for tests to read | not bound; never written or read |
| Seal | KMS + TSA when `KMS_KEY_ARN` is set (as on `esign-dev`), else the HMAC test seal (`TEST_SEAL_KEY`, local) | KMS + TSA only; no fallback |
| Pages that may call the signing API | the Worker's own `/sign`, plus `SIGNING_PAGE_ORIGINS` (local UI development) | the Worker's own `/sign` only |
| Origins that may embed `/sign` (`SIGNING_PAGE_FRAME_ANCESTORS`) | https, or http on a loopback host | https only |
| Signing, `/demo` and the cron | on once `OTP_KEY` is set and the test mailbox is bound | on once fully configured; otherwise off, and each cron run logs what is missing, by name (`prodProblems`) |

prod is fully configured when `OTP_KEY`, the `SEND_EMAIL` binding, `MAIL_FROM` and `KMS_KEY_ARN`
are set, and neither `MAIL_SINK` nor `TEST_MAIL` is. While signing is off, the signing routes,
`/sign`, `/demo`, recipient views, certificates, delivery PDFs and the test mailbox answer 404.

When a dev deployment has a sink, its `send_email` binding is pinned to the sink with
`destination_address`, so the Worker cannot mail anyone else. Without a sink (as `esign-dev` now
runs) and on `esign-prod` it is not pinned and mails each recipient.

## Settings and secrets

Variables (set in `wrangler.jsonc` locally, generated by `scripts/deploy.ts` for a deployment):

| Variable | Meaning |
|---|---|
| `ESIGN_ENV` | `dev` or `prod` |
| `COMPLETE_AFTER_SIGN` | `true`: render each signature and seal the envelope in the background after the sign request. Off, only the cron finishes envelopes |
| `SIGNING_PAGE_FRAME_ANCESTORS` | Space-separated origins allowed to frame `/sign` (at most 10 kept) |
| `SIGNING_PAGE_ORIGINS` | dev only: other origins that may host the signing page (`.dev.vars`: `http://127.0.0.1:5173`) |
| `MAIL_FROM`, `MAIL_SINK` | The sender (a Cloudflare Email Sending domain); dev's optional sink mailbox |
| `KMS_KEY_ARN`, `KMS_PUBLIC_KEY`, `AWS_ROLE_ARN` | The managed seal: the P-256 signing key, its SubjectPublicKeyInfo (base64, pinned) and the role that may sign with it |
| `KMS_TRUSTED_KEY_SHA256`, `TSA_SIGNER_SPKI_SHA256` | Optional: SPKI SHA-256s of earlier KMS keys still trusted to verify old seals, and of extra DigiCert TSA signers |

Bindings: `DB` (D1), `ARTIFACTS` (R2), `TEST_MAIL` (R2, dev only), `SEND_EMAIL`, `ASSETS` (the
built pages in `dist-ui`).

Secrets: `OTP_KEY` (the one-time codes' pepper, at least 32 characters, both environments),
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` (the managed seal's IAM user) and, locally only,
`TEST_SEAL_KEY` (the HMAC test seal, at least 32 characters), and optionally `PROVISIONING_KEY`
(lets the host create its organizations' tenants, see below). A deployed Worker seals with KMS and
TSA, so it needs no `TEST_SEAL_KEY`. A managed seal configuration that is incomplete is an error,
never a silent fallback.

## What runs on its own

- **After each sign request** (`COMPLETE_AFTER_SIGN=true`): the envelope's pending signatures are
  rendered and, after the last, the envelope is sealed and the signed copies sent, in the
  background (`waitUntil`).
- **Cron** (`*/5 * * * *`, `triggers` in `wrangler.jsonc`): expires envelopes past a recipient's
  deadline; finishes up to 25 envelopes, picked at random, that are `FINALIZING` or `IN_PROGRESS`
  with work left (a pending signature, or no unsigned active task); and sends signed copies still
  owed for completed envelopes created in the last seven days. A signature that fails to render
  keeps `attempts` and `last_error` and is retried on every run. See "How writes commit" in
  [README.md](README.md#how-writes-commit).

## Managed seal (KMS + TSA)

How the seal works is in [README.md](README.md#evidence-hash-chain-and-seals). Operations:

- The Worker cannot hold an AWS role, so it holds the key of an IAM user that may only assume one
  role, and that role may only sign with the key (`src/seal/kms.ts`). The assumed-role
  credentials are cached per Worker isolate. `scripts/aws-dev-signer.sh` creates the user and role
  for the signing key and, with `--create-access-key`, stores a new access key directly as the
  Worker's `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` without printing it (one key per Worker;
  IAM allows two per user).
- **Rotating the KMS key**: deploy the new key's ARN and public key, and add the old key's SPKI
  SHA-256 to `KMS_TRUSTED_KEY_SHA256` so envelopes sealed with it still verify.
- **DigiCert rotating its TSA signer**: add the new signer's SPKI SHA-256 to
  `TSA_SIGNER_SPKI_SHA256`. The TSA URL, root and policy are fixed in `src/seal/tsa.ts`.
- **Never change `TEST_SEAL_KEY`** while local envelopes sealed with it should stay verifiable: the
  certificate check recomputes the local seal with the current key.

## Test mailbox

In dev every code is also kept in the `TEST_MAIL` bucket (`test-mail/<messageId>.json`, plaintext,
never deleted). `GET /v1/test-mail/:messageId`, with the tenant's management key, returns
`{to, otp}` for a code sent to one of that tenant's recipients (404 for any other). The recipient
page does not show the message id; test scripts read it from the code form's
`data-test-message-id` attribute. prod has no test mailbox and the route is 404.

## Try it: /demo

`<worker origin>/demo` drives the whole flow from one page on the Worker's own origin: paste a
tenant management key (kept only in that tab's sessionStorage), upload a synthetic PDF, choose a
signature page added after the last page or signature fields placed in the editor, add one or two
signers, then sign each signer's page embedded below. Codes and copies go where the environment
sends them (the sink on a dev with one; otherwise the signers themselves). Once the envelope is completed, view
the signed PDF with its certificate and the completion certificate. The tenant must list the
Worker's own origin as a console origin (for the editor): `--console-origin <worker origin>` when
provisioning it. `/demo` is never framed by another site.

## Run it locally

```sh
npm ci
npx vite build                       # dist-ui: the recipient page, editor, demo and assets
npm run db:migrate:local
cp -n .dev.vars.example .dev.vars    # synthetic test keys; never deploy them
node scripts/provision-tenant.ts --tenant <tenant id> \
  --console-origin http://localhost:3000 \
  --key-file <path outside the repo> --local
npm run dev -- --test-scheduled      # 127.0.0.1:8787; /__scheduled runs the cron once
```

A host product's console then uses `http://127.0.0.1:8787` as the E-sign base URL and
`http://127.0.0.1:8787/sign` as the signing page URL, with the key from the key file.
`SIGNING_PAGE_FRAME_ANCESTORS` in `wrangler.jsonc` must list the host's origin. For a walkthrough
with `curl`, see "Run locally" in [README.md](README.md#run-locally).

## Deploy

No account or resource id is kept in this repository. `scripts/deploy.ts` generates the Wrangler
configuration of `esign-<target>` for one run (into `.deploy/`, ignored) from the environment:

- every resource is named after the target: the Worker and the D1 database `esign-<target>`, the
  R2 bucket `esign-<target>-artifacts` and, for dev only, `esign-<target>-test-mail`;
- the D1 id is looked up by name;
- the target decides `ESIGN_ENV`; dev pins `send_email` to the sink when `ESIGN_MAIL_SINK` is set
  (else it mails recipients), prod binds no test mailbox and sets no sink;
- `COMPLETE_AFTER_SIGN` is `true`, the cron comes from `wrangler.jsonc`, `workers_dev` is on,
  preview URLs are off and observability is on.

It refuses to deploy while `OTP_KEY`, `AWS_ACCESS_KEY_ID` or `AWS_SECRET_ACCESS_KEY` is missing on
the Worker, then applies new migrations (`wrangler d1 migrations apply --remote`) and deploys.
`--dry-run` shows the bindings without deploying; `--config-only` only writes the configuration;
`--bundle dist` deploys an already built `dist/worker.js` as is.

| Setting | Environment variable |
|---|---|
| Cloudflare account and token | `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN` |
| Sender of every message (a Cloudflare Email Sending domain) | `ESIGN_MAIL_FROM` |
| dev only, optional: the one mailbox that receives every message (refused for prod) | `ESIGN_MAIL_SINK` |
| Origins allowed to embed `/sign` (space-separated; https only for prod) | `ESIGN_FRAME_ANCESTORS` |
| Managed seal: KMS key ARN, its public key (base64 SPKI), the signing role (required for both targets) | `ESIGN_KMS_KEY_ARN`, `ESIGN_KMS_PUBLIC_KEY`, `ESIGN_AWS_ROLE_ARN` |

Secrets stay on the Worker and never pass through the deploy: set `OTP_KEY` once with
`wrangler secret put OTP_KEY --name esign-<target>` (random), and the AWS key with
`scripts/aws-dev-signer.sh --create-access-key` (`ESIGN_WORKER=esign-prod` for prod).

- **CI** (`.github/workflows/esign.yml`, see [CI.md](CI.md)): a push to `main` or a `feat/esign-*`
  branch deploys `esign-dev` once the repository variable `ESIGN_DEV_DEPLOY` is `true`; **Run
  workflow** deploys `dev` from any branch or `prod` from `main` only. The deploy job runs in the
  GitHub environment `esign-dev` or `production`, each holding the secret `CLOUDFLARE_API_TOKEN`
  and the variables above under the same names (`ESIGN_MAIL_SINK` in `esign-dev` only). It runs
  `node scripts/deploy.ts --target <target> --bundle ... --assets ...` on the archive the
  credential-free checks job built.
- **By hand** (only with authorization for that account, and only with synthetic data): set the
  variables above, then `npm run build && node scripts/deploy.ts --target dev --bundle dist`.
- **First deployment of a target**: create its D1 database and R2 buckets once
  (`wrangler d1 create esign-<target>`, `wrangler r2 bucket create ...`), set the secrets, then
  deploy.
- **Migrations** have been edited in place during development ([PROGRESS.md](PROGRESS.md)), and
  Wrangler does not re-apply a migration it has already recorded. A database migrated from earlier versions of these files
  does not have the current schema; recreate it (it may hold synthetic data only) rather than
  migrating it. See [DEPLOYMENT-RUNBOOK.md](DEPLOYMENT-RUNBOOK.md).
- **A host organization**: `node scripts/deploy.ts --target dev --config-only`, then
  `node scripts/provision-tenant.ts --tenant <org id> --console-origin <host console origin>
  --key-file <path> --remote --config .deploy/wrangler.dev.json`, and give the host the key, the
  Worker origin as base URL and `<Worker origin>/sign` as the signing page URL. Every tenant signs
  on the same origin (for example `https://esign.example.com`). Running it again with a new key
  file adds a second key (rotation); revoke old keys by setting `api_keys.revoked_at`.
- **A host organization, provisioned by the host**: with the Worker secret `PROVISIONING_KEY` set
  (random, at least 32 characters; `wrangler secret put PROVISIONING_KEY --name esign-<target>`),
  the host creates each organization's tenant itself the first time that organization uses E-sign:
  `POST /v1/tenants` with `Authorization: Bearer <provisioning key>` and `{"tenantId": "<org id>"}`
  returns `201 {"tenantId", "apiKey"}`, the key returned this once (only its SHA-256 is kept).
  The tenant's editor origins are the frame ancestors (`ESIGN_FRAME_ANCESTORS`). The provisioning
  key reads nothing and cannot take over a tenant in use: once the tenant has a template, an
  envelope or an editing session, the answer is `409 tenant_in_use`. Before that, asking again
  revokes the earlier keys and issues a new one (a host that lost the response before saving the
  key recovers this way), so the host must not ask concurrently for one organization. Without the
  secret the route is 404. See `src/tenant-provisioning.ts`.
- **Editor origins**: each `--console-origin` (repeatable) must be a bare origin: https, or http on
  `localhost` or `127.0.0.1`, lowercase, with no path, quote or other punctuation; anything else is
  refused before any SQL is generated. They are merged into the tenant's `editor_origins_json`
  (a JSON array; the column's CHECK refuses anything else): an origin already listed is skipped,
  existing entries and their order are kept, and new ones are appended, so a repeated run changes
  nothing. `--dry-run` prints the SQL. Provisioning only
  adds origins; to remove one, write the tenant's list without it (for example with
  `json_remove`). That takes effect at the next check: codes, editor pages and tokens of editing
  sessions for that origin stop working and no new session can start for it.

Notes from the first deployment:

- Do not enable Cloudflare Email *Routing* on a sending domain whose mail is handled elsewhere: it
  replaces the domain's MX records. Email *Sending* only adds records on its `cf-bounce` subdomain.
- A cron trigger can take up to 15 minutes to start after it is first deployed or changed;
  `wrangler tail esign-<target>` shows each run (`"cron": "*/5 * * * *"`).
- `/__scheduled` exists only under `wrangler dev`; it is 404 on Cloudflare.
- The Worker has no rate limiting of its own beyond the OTP budget; put Cloudflare rate limiting
  rules on `/v1/signing/otp*` and `/v1/page-sessions/exchange` before inviting anyone outside the
  team.
