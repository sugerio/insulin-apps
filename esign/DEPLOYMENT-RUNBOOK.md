# Isolated Cloudflare preparation (not deployment approval)

These reference templates are deliberately unbound and unreachable; they do not supply resource identifiers, routes, secrets, enablement, limits, or real origins. They are not deploy-ready. Do not deploy, create or change cloud resources, migrate a database, send email, or call a TSA without separate explicit authorization and independent security review. Use synthetic documents and identities only. The local experiments are not production signing, sealed evidence, identity verification, or a retention guarantee.

## Separate-Worker topology to review

This section and the concrete worksheet below describe the separate-Worker topology only. For the alternative consolidated topology use the distinct section and checker below; neither worksheet verifies actual infrastructure.

* `deployment-templates/candidate.jsonc`: isolated candidate Worker, public fetch only health; named `PrivateManagement`, `PrivateEditor`, and `PrivateRecipient` entrypoints. Do not expose the named bindings directly or attach local demo assets/mailbox. Fresh, isolated D1 `DB` and R2 `ARTIFACTS` would be required for the experimental flows; they do not provide atomic cross-store writes or immutable storage.
* Three independent gateway templates bind respectively `PRIVATE_MANAGEMENT` → `PrivateManagement`, `PRIVATE_EDITOR` → `PrivateEditor`, and `PRIVATE_RECIPIENT` → `PrivateRecipient` on that Worker. Each requires distinct `RATE_LIMITER` and `LOCATION_RATE_LIMITER` namespaces. Binding alone does not authorize callers. The latter two additionally require exact canonical HTTPS `TRUSTED_EDITOR_ORIGINS` / `TRUSTED_RECIPIENT_ORIGINS`. Do not assume client-IP header provenance; the independent fixed-key budget reduces spoofed-key bypass but does not establish identity; the limiter is location-local, not a global quota. Management requires a protected backend and human/tenant authorization; origin and CORS are not identity.
* Host candidate editor and recipient pages on a reviewed standalone HTTPS origin. `npm run build:candidate-assets` requires exact HTTPS gateway origins and creates a new dedicated output directory; it refuses an existing directory or a symlinked parent. Remove old artifacts manually only after verifying their contents. NODE_ENV must be unset or production. It creates a paired `worker.mjs` and `client/` asset directory: the worker embeds the exact generated paths, content hashes, MIME types and build origins, and fails closed if the runtime gateway origins differ or asset bytes change. The reference Worker configuration is inert and has no asset binding or enablement. Configure the paired client directory as `ASSETS` with Worker-first routing for every request, and explicit matching gateway origins only after independent review; verify no platform asset route bypasses the Worker; never publish `dist-ui` or expose the client directory outside this Worker. The Worker denies framing, prevents caching HTML, and permits connections only to the configured gateways. This is not deployment authorization or evidence of production identity, storage or edge controls. The host must authenticate and authorize users, securely deliver one-use fragments, and avoid logging tokens or codes.

Do not retry an issuance, creation, preparation, save, or mail send on timeout, invalid response, missing output or any other failure. A mutation may have committed even when its response or output file is lost. Stop, establish settlement, and privately inspect state under a separately reviewed recovery procedure; a result query is read-only, and an empty result while a request is in flight is inconclusive. The client intentionally does not automatically recover or print server error bodies.

### Local supervised command controller

`node scripts/local-controller.mjs /absolute/path/to/config.json` runs in the foreground on POSIX systems. It is an independent local tool, not an upload or deployment client. A trusted operator must pre-approve the executable and every argument in the configuration, protect the file from modification, and supervise the process. Example shape (replace every command with independently reviewed local commands):

```json
{
  "timeoutMs": 30000,
  "cleanupTimeoutMs": 10000,
  "run": ["/absolute/path/to/approved-command", "argument"],
  "disableIngress": ["/absolute/path/to/approved-disable-command"],
  "rollback": ["/absolute/path/to/approved-rollback-command"],
  "verify": ["/absolute/path/to/approved-verification-command"]
}
```

Each array is an executable followed by literal arguments; no shell is invoked. Use absolute executable paths and commands that terminate and report failure with a nonzero exit status. The run timeout applies to `run`; the cleanup timeout applies separately to each cleanup command. After `run` exits, fails, times out, or the controller receives SIGINT/SIGTERM, it attempts disable, rollback, and verification in that order, even if an earlier step fails. Verification must independently check the desired disabled and rolled-back state and return nonzero if it cannot establish it. Exit zero requires all four commands to succeed without a signal or timeout. Invalid or unreadable configuration is rejected before any command starts, so it cannot trigger cleanup.

Before advancing from any command, the controller sends SIGTERM to its remaining POSIX process group, escalates to SIGKILL after a short wait, and waits a bounded time for the group to disappear. It reports failure if disappearance cannot be confirmed, including when unreaped zombies keep the group visible. Timeouts and signals also trigger this termination; cleanup commands have their own timeouts and are not interrupted by further SIGINT/SIGTERM. These are best-effort safeguards, not a guarantee: SIGKILL, controller or host crashes, escaped child processes, machine suspension, network failure, or a command reporting success incorrectly can prevent or invalidate cleanup. The controller cannot verify remote state itself and cannot undo effects of processes that survive it. Keep an independent recovery path and verify state externally; do not rely on this process as a security boundary or unattended safety mechanism.

### Future isolated synthetic rollout: reviewed upload checklist

This is a review procedure, not a runnable deployment command. The user-authorized test is limited to the approved isolated synthetic scope; independent review, fresh preflight and a reviewed execution/recovery procedure remain necessary. The retained staged review marks its bundle offline-only; do not run old fail-closed wrappers or treat that label as upload approval. The private rollback script pins a historical version, not necessarily the current baseline.

Cloudflare describes a version as capturing code, assets and bindings: https://developers.cloudflare.com/workers/versions-and-deployments/ . The version API provides metadata; no documented arbitrary version-content GET is established here. The following standard does not independently prove remote executable bytes. If the organization requires remote executable-byte verification, keep the rollout blocked until an independently reviewed method meets that requirement; do not substitute metadata or public asset checks.

* Independently review the exact staged manifest, config, Worker bytes and all assets, source revision and build provenance. Verify `SHA256.txt`, `ALL-SHA256.txt`, `SOURCE-SHA256.txt` and the source fingerprint against the reviewed inputs and current source; source inventory does not cover installed dependency bytes. Investigate any difference, missing file or unexpected input. Protect the staged tree and configuration against modification throughout verification and upload; do not rebuild or substitute the reviewed bundle. Independently establish installed Wrangler behavior and the exact asset/config pairing before proceeding.
* With all ingress disabled and verified absent, perform a fresh upload of the exact reviewed bundle using Wrangler `--no-bundle`, not a historical version or an implicit rebuild. Record privately the upload result, version ID, timestamp and version metadata, and compare expected bindings and configuration to that metadata. Verify the active deployment and traffic allocation separately. After separately approved enablement, compare served public asset bytes to the pinned staged assets, checking every expected path and rejecting bypass or unexpected response. These checks establish neither remote executable byte identity nor integrity of untested responses. Stop on any mismatch, uncertain result or inability to establish a check; no mail may be sent.
* Freshly verify account, target, single 100% active version, all version metadata and expected bindings/pins, routes, domains, workers.dev and previews, migrations, dedicated D1/R2 state, tenant origins, existing consumers and limiter namespace collisions. Record old active version metadata separately from current script settings: they can differ and neither is a substitute for the other. Establish sender eligibility and sink ownership privately. Secret binding metadata does not establish its value or continuity. Verify the existing API mail policy remains two per day and lifetime limits 10/3, with TSA off. Stop on uncertainty or insufficient quota.
* Protect the management key throughout; never print, regenerate, rotate or expose it in arguments, logs, the repository or browser. Use the approved private backend secret channel. Resolve the OTP pepper discrepancy before enablement: preserve continuity if independently established, or rotate only with ingress off and verified zero outstanding challenges, after reviewing consequences and authorizing rotation. Secret values must not be printed. Review current Wrangler semantics and use `versions secret` or a vetted private `--secrets-file` workflow for version-specific secret injection; ensure the intended uploaded version actually has the required binding without exposing values. Do not assume script-level secrets carry into the selected version. Stop if secret continuity or injection cannot be established.
* Capture a fresh private baseline and separately review the rollback target and disable/restore procedures. The retained rollback script must not be assumed current or sufficient. Disable workers.dev and previews regardless of run outcome, rollback, then independently verify both restored version/pins and absence of all ingress (including routes and domains). A failed or unverifiable step requires manual incident escalation; rollback cannot unsend mail or undo storage writes.
* A future supervised controller config must use explicit absolute executable/argument arrays, no shell, a 1,200,000 ms run timeout and bounded cleanup timeouts. Its run must stop on any failed precondition; cleanup runs disable, rollback, verify even on failure or interruption. Keep the foreground operator present, private artifacts mode 0600 in a private directory, sanitized logs only, and a separately authorized manual recovery path.
