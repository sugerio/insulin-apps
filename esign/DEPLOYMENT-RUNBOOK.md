# Isolated Cloudflare preparation (not deployment approval)

E-sign runs as one Worker, `src/worker.ts`. How it is configured, deployed (`scripts/deploy.ts`) and given tenants (`scripts/provision-tenant.ts`) is described in [WORKER-MODE.md](WORKER-MODE.md). The earlier candidate Worker, its three gateways, the consolidated Worker, the Access-protected internal demo and their deployment templates and worksheets were removed. Do not deploy, create or change cloud resources, migrate a database, send email, or call a TSA without separate explicit authorization. Use synthetic documents and identities only.

## Stop and rollback planning

Disable Worker ingress first, revoke affected credentials and stop issuing sessions under an approved incident process. Preserve D1 rows and R2 objects for investigation; disabling a route does not revoke already issued credentials or undo writes. Do not automatically delete orphaned objects, reservations or retained facts, and do not infer delivery or completion from a lost response. Establish separately authorized recovery, monitoring, audit and retention procedures before any cloud operation. No production readiness or finalization is implied.

## Offline preparation of the first management credential (no cloud action)

This is preparation only, not authorization to change D1, enable APIs or deploy. The management key grants tenant-wide management access; it is not a browser credential. The separately authenticated host backend must authorize each caller and tenant before using it. No endpoint provisions or elevates keys dynamically. Independent security review and specific authorization are required before the later D1 write and before enabling management access.

Before any later write, independently verify the private account, the exact existing isolated D1 identifier and its binding to the intended single Worker, Worker version, isolation, ingress, and absence of unexpected known consumers; stop on any mismatch. Establish an operational boundary for the entire preparation, write, verification and recovery procedure: identify and coordinate all known D1 writers and consumers, excluding other writes and consumption until the procedure is complete. Stop if that boundary cannot be established or maintained. This coordination cannot prove the absence of external privileged users; account-privileged actors remain a trust assumption and can change state despite these controls. Review the exact source revision, all forward migrations and private D1 migration ledger/schema against it; this helper neither applies nor verifies migrations. Do not apply migrations to a retained database by assumption. Check that exactly one tenant exists and it is the intended tenant, and that **no** `api_keys` row exists, including revoked rows. Tenant creation and any migrations require separately reviewed authorization; this procedure does not create a tenant. Do not use a shared or production database. Record the verification privately without credentials or identifiers in this repository.

On a trusted operator machine, disable shell tracing and terminal/session recording, use an encrypted private filesystem and create a new owner-only directory outside any checkout, backup or sync location. With a non-secret tenant ID (letters, digits, `_` or `-` only), run from `esign`:

```sh
python3 scripts/prepare_management_key.py /absolute/private/owner-only-directory tenant_id
```

The Python 3 helper requires POSIX directory-descriptor and no-follow support. It rejects symlinks, group/other-writable ancestors and directories not owned by root or the operator; the final directory must be operator-owned and owner-only. It pins the checked directory for creation and cleanup and rechecks path identity before success. This is a point-in-time check: a subsequent rename can invalidate the delivery path. Keep the entire path stable and exclude untrusted same-user processes, ACL grants, mount changes and privileged actors throughout preparation and use. After any failed or interrupted preparation, stop and privately inspect the original, pinned directory for **both** outputs, even if no cleanup warning appeared; termination can leave partial files without a warning. Locate the original directory securely if its path changed, do not assume the current pathname still identifies it, and securely remove any outputs according to the operator's storage policy.

The offline helper makes `management-key` and `management-key.sql` exclusively, both mode 0600; it refuses an existing filename and will not print the bearer or hash. The bearer is 32 random bytes encoded as unpadded base64url; SQL contains only its SHA-256 hex digest. Never copy the bearer into a command argument, shell variable/history, log, ticket, repository, browser or SQL; the backend must ingest the secret file through its approved private secret-management channel without logging. Protect the SQL file as sensitive too. Restrict directory access, telemetry and backups; mode bits alone do not protect against privileged users, ACLs, endpoint compromise or snapshots. Do not generate real credentials until the environment and private handling are approved.

After separate authorization and fresh verification, an operator may apply the generated SQL file with the reviewed D1 tooling's file-input option (for Wrangler, `d1 execute` with `--remote` and `--file`), targeting the privately verified database explicitly. Do not use `--command`, paste SQL, or log the file contents; protect provider and CLI diagnostic logs. The single atomic insert checks that exactly one tenant exists and it is the intended tenant, and that the `api_keys` table is entirely empty; zero, wrong or extra tenants, any existing key (including revoked), or a repeated/concurrent first-key insert fails rather than adding a duplicate. These are point-in-time conditions in the insert, not a claim of global exclusive control: state can change after either the tenant or key statement. Operators must inspect and monitor the state and stop on any mismatch; separate reads cannot establish an enduring snapshot. This is deliberately first-key-only, not a rotation or recovery procedure. Verify the resulting row count, tenant and active status privately without displaying the hash; independently verify the intended backend can authenticate only after separately authorized enablement. If the write result is uncertain, stop without automatic retry and establish that the original request has settled before interpreting state or considering a later attempt. An empty read is inconclusive while the request may still be in flight; if settlement cannot be established, remain stopped. Once settled, inspect state before any deliberate retry; never replace a credential blindly. If the file is lost or exposure is suspected, stop and follow a separately reviewed revocation/recovery plan. Transfer the secret privately, then securely dispose of temporary files according to the operator's storage policy; deletion is not guaranteed erasure on modern storage. No real email or TSA operation is involved.

## Local synthetic first-tenant fixture only

`test/first-tenant-provision.ts` is a test-only helper for an in-memory Miniflare D1 using the migrated tenant/key schema. It creates only the fixed synthetic tenant and is not a CLI, endpoint, remote provisioning procedure, or authorization to access cloud D1. Its one guarded insert fails if any tenant or any key exists. The existing first-key generator remains separate and requires exactly the intended tenant and no keys. These are **two separate writes**, not an all-or-nothing setup; a tenant with no key has no management access.

For local synthetic setup and recovery, coordinate all known D1 writers and consumers and exclude other writes and consumption throughout; stop if that operational boundary cannot be established or maintained. Privileged actors remain a trust assumption, not something an inspection can exclude. After an uncertain local tenant or key write, stop without automatic retry and establish that the original request has settled before interpreting state or considering a later attempt. An empty read is inconclusive while the request may still be in flight; if settlement cannot be established, remain stopped. After an uncertain tenant write has settled, inspect both tables: if exactly the fixed synthetic tenant exists and there are no keys, the tenant write completed and the separately generated first-key SQL may be applied once. If both tables are empty, the tenant write did not persist; investigate the failure before a deliberate new attempt. Any other state, including a different or extra tenant or any key, is not a clean first-tenant state: stop and investigate, without resetting or deleting data. After an uncertain key write has settled, inspect key count, tenant, active status and whether its hash matches the original generated SQL, without displaying either hash: one matching active key means the write completed; no key means investigate before a deliberate new attempt using the original retained generated files; any other state or lost/exposed files requires a separately reviewed recovery plan. Never generate a replacement blindly. These observations are point-in-time only; concurrent or privileged mutation can change state after either statement or inspection and invalidates any enduring inference. Inspect and monitor, and stop on any mismatch; no global exclusive-control guarantee is established. None of this authorizes remote changes or enabling access.

## Local supervised command controller

`node scripts/local-controller.mjs /absolute/path/to/config.json` runs in the foreground on POSIX systems. It is an independent local tool, not an upload or deployment client. A trusted operator must pre-approve the executable and every argument in the configuration, protect the file from modification, and supervise the process. Example shape (replace every command with independently reviewed local commands):

```json
{
  "timeoutMs": 30000,
  "cleanupTimeoutMs": 10000,
  "run": ["/absolute/path/to/approved-command", "argument"],
  "disableIngress": ["/absolute/path/to/approved-disable-command"],
  "rollback": ["/absolute/path/to/approved-rollback-command"],
  "verify": ["/absolute/path/to/approved-verification-command"]
}
```

Each array is an executable followed by literal arguments; no shell is invoked. Use absolute executable paths and commands that terminate and report failure with a nonzero exit status. The run timeout applies to `run`; the cleanup timeout applies separately to each cleanup command. After `run` exits, fails, times out, or the controller receives SIGINT/SIGTERM, it attempts disable, rollback, and verification in that order, even if an earlier step fails. Verification must independently check the desired disabled and rolled-back state and return nonzero if it cannot establish it. Exit zero requires all four commands to succeed without a signal or timeout. Invalid or unreadable configuration is rejected before any command starts, so it cannot trigger cleanup.

Before advancing from any command, the controller sends SIGTERM to its remaining POSIX process group, escalates to SIGKILL after a short wait, and waits a bounded time for the group to disappear. It reports failure if disappearance cannot be confirmed, including when unreaped zombies keep the group visible. Timeouts and signals also trigger this termination; cleanup commands have their own timeouts and are not interrupted by further SIGINT/SIGTERM. These are best-effort safeguards, not a guarantee: SIGKILL, controller or host crashes, escaped child processes, machine suspension, network failure, or a command reporting success incorrectly can prevent or invalidate cleanup. The controller cannot verify remote state itself and cannot undo effects of processes that survive it. Keep an independent recovery path and verify state externally; do not rely on this process as a security boundary or unattended safety mechanism.
